Basic and Advanced.
One product, two jobs.

Operators arrive to answer one of five questions. Basic answers the first four completely; Advanced answers the fifth and everything under it. Nothing is removed — the machinery is simply not in the room while you assign a bundle.

01 · Navigation

Three audiences, one structure

Advanced appends to Basic — same items, same order, nothing renamed and nothing above them. A section with nothing in it keeps its seat and shows a hollow zero. A badge going from 0 to 12 must never move the item under your cursor.

Structure never moves

Today's sidebar injects a Drift section at the top when the count is non-zero, pushing every other item down under the cursor. Here, Unexplained access has a fixed seat inside Review whether it reads 12 or 0.

Badges are fed scalars

The rail polls a compact endpoint — it must never download every pending request just to render a "3".

GET /api/v1/governance/indicators
→ { pending_requests: 3, expiring_grants: 1,
    pending_propagation: 2, drift: 12 }
Sub-navigation carries the load

Access shows Projects / Roles / Apps in the rail; People uses in-page tabs on the person detail. The rail stays four items deep in Everyday.

02 · The switch

Reveals in place. Never navigates.

It sits top-right, beside the account and away from the rail, so it reads as "what I'm looking at" rather than a destination. The URL is identical on both sides. Persisted as ui_view — never mode, which is already taken.

Labels — decided
Basic Advanced

Shipping. Everything in this document uses these two words. Internally the preference is ui_view: basic | advanced — never mode.

Access Machinery

Names the object rather than the cadence. Sharper — but "Access" collides with the Access nav group.

Everyday System

Considered and set aside. Sorted work by cadence rather than depth; "System" also collides with the System nav group in Advanced.

03 · Signature component

Access source

Three kinds, fixed vocabulary, always in this order. The dot carries the meaning before the word does — solid for something a person did, ring for something a bundle did, dashed for something the system did on its own. Dashed means nobody clicked it.

04 · Landing

Today — work, not a summary

Every block is something you can finish. No counts you can't act on, no charts. Basic shows two blocks; Advanced appends two more. If all of them are clear, the page says so in one line and gets out of the way.

05 · People · E3

People, and one person’s access

The highest-traffic screen in the product. Grouped by project, granted above automatic, every row carrying its source. Bundle chips state membership and nothing else — no inline ✕, because one misclick should never strip a dozen roles.

06 · E2

Who can currently use the laser cutter?

Role → members, with every row carrying its source. There is never a generic "Revoke role." The action is named after the thing being removed, and the confirmation states what the person is left holding.

07 · E1 + E2 index + Apps

Projects, and the roles inside them

A project is a boundary that owns roles; an app is a thing that receives a token. They are not one-to-one, and the list says so on every row. The cross-project role index is honest about being partial rather than letting someone conclude a role doesn't exist and make a duplicate.

08 · E4 + E5

Giving access, with the consequences visible

Bundles expand to roles and rules cascade further, so the preview isn't a footnote — it's the body of the panel. Expiry is real: a sweep revokes it, so the date field gets proper attention and "in 3 days" shows up on the person's page.

09 · E6

“My app isn't seeing the roles it expects”

The most technical thing in Everyday, and it earns its place by being the fastest way to end that conversation. Format on the left, dry run on the right, and the output reads like a receipt.

10 · E7 + member surface

Two sides of the same request

Members get two destinations and land on their own access — the one screen that explains why they can badge into the laser bay. The view switch isn't rendered for them, and every operator-only route 403s underneath.

11 · Every list view

Four states, no exceptions

Degraded is the one that matters most: when the backend has fallen back to demo data, every number on screen is fiction. That banner is persistent, unmissable, and cannot be dismissed.

12 · S5

Access map — a neighbourhood, not a hairball

The current graph is unreadable because it draws everything at once. Pick one node and the map answers two questions instead: what feeds this, and what does this feed. One hop each way by default, expandable per node.

13 · Themes

Dark is home. Light is daylight.

Same geometry, same spacing, same components — the accent shifts value with the ground so it keeps its weight: #7f5af0 carries a near-black room, #5b3fd6 carries a paper one. Nothing about the layout changes between them.

14 · S6 · highest stakes

Unexplained access

Access that exists in the identity provider which Syndra cannot explain. Every row has to answer two questions in about two seconds: what is this, and what happens if I revoke it. So the evidence is on the row, not behind a click, and the three resolutions are always in the same order.

15 · S7

Expiring access — one action only

Its own destination, not an audit tab: audit is a record you consult, this is time-boxed work you act on before a deadline. Doing nothing is not an action and must not be drawn as one — no dismiss, no "let it lapse", no secondary control that looks like it submits something.

16 · S1 + S2b

Changing the machine that acts on everyone

Assigning a bundle to one person is Basic. Editing what a bundle contains changes access for every holder at once, so it lives here — with the impact preview above the fold, not in a footnote.

17 · S2 + S3 + S4

Rules, the queue they fill, and the record of what they did

One causal chain, three screens, read left to right: a rule fires → a write queues → the write lands and is recorded. Each screen links to its neighbours by the same cascade id, so you can follow one event the whole way.

18 · S8–S11

The forensic floor

Four read-mostly screens for when something has already happened. None of them is a dashboard: Today owns actionable summary, and a second one here would make it ambiguous which is authoritative.

19 · Add-on platform · Navigation

Three rows in, one row out

The add-on platform adds a destination to each of Review, System and the member rail, and removes one that named a deleted subsystem. Two of those additions exist specifically to keep the rail still: target rows are built from deployment configuration rather than from data, and the member storage row appears whether or not that member can reach anything.

Hardware sync is gone

It named the LLDAP bridge, which is deleted. A nav row for a subsystem that no longer exists is worse than a missing one — an operator clicks it before they read anything.

Target rows are configuration, not data

A row appears because the deployment registered an add-on — never because this operator can see something. And no badge: a count on these rows would be data driving structure, which is the one thing the rail does not do.

targetNav(targets) ← GET /api/v1/targets
The member row is ungated

Gating it on entitlement would make the rail move as somebody's roles change, and it answers the wrong question. A member without access is asking whether they can get it — a missing row does not answer that.

But not every add-on earns a member destination. TrueNAS does, because there is something there to look at and a password to set. Unifi Access does not — a door is something you walk through, so it belongs under the role that opens it. That judgement is made per add-on, deliberately, rather than by rule.

Withdrawn access is a destination

Never a tab inside drift. Drift is access that appeared and cannot be explained; this is access somebody decided to take away that is still there. Different question, different room.

20 · Member › TrueNAS · /storage/[target]

Three states, and the middle one is ordinary

A two-state page — access or no access — lies to the member in the middle. Add-on changes wait for an operator to resume the drain, so “recorded, not created yet” is the ordinary experience of every new member until that happens. The same three-node spine opens all three states, so they read as one progression rather than three unrelated panels.

21 · Advanced › System › ‹target› · /system/targets/[target]

Four questions about one add-on

Is it answering, whose accounts are on it, what can it actually do, and what state has somebody put it in. In that order, because each answer changes what the next one means — capabilities read differently once you know the circuit is open.

22 · Advanced › Review › Withdrawn access

Two populations, never one count

Access somebody decided to take away that is still there. Merged into a single number, a healthy queue of five-minute-old rows hides a revocation that failed permanently three days ago — so the two are rendered apart, under headings that say which is which.

The badge escalates on a flag, not a count

Any spent row escalates immediately; a queued one escalates after 24 hours. An operator reading “3” cannot tell those apart, so the rail is fed the decision rather than the number.

revocations_escalated: true
→ Withdrawn access · 3 · danger
Queued is not succeeded

Every apply response carries a summary whose succeeded is always zero — present precisely so a client cannot default it. Nothing an operator does on these screens reaches a target directly.

Provisional is not applied

A plan computed while the target was unreachable is labelled with the age of the state it was computed against. “Computed against last-known state” with no number is a label nobody can act on.

Truncated is not empty

A capped read reports what it saw. Absence proves nothing, and a list that quietly stops is worse than one that says where it stopped.

A confirmation is a refusal

account.adopt, account.purge and the revocation composition are refused by the backend without one. A dialog only the frontend enforces is a suggestion.

23 · Plan, then apply · 9.3–9.6

The plan is the thing you approve

Rehearse, read, apply. Two steps in place — not a wizard, because an operator who has read the plan should not have to walk forward to reach the button. Apply carries the plan_id, never the original submission, so what gets queued is the thing that was on screen. This is now the plan-then-apply pattern: bulk grants and drift triage move onto it rather than the other way round, so there is one shape for “show me what this does before it does it” everywhere in the product.

24 · Mapping management · 9.7–9.8

Every version, and who is affected by changing it

A mapping ties a role to what it reaches on an add-on, so editing one moves access for everyone holding that role. Nothing lands without a plan first — edit, delete and rollback all rehearse — and the blast radius is a number in a sentence the operator has to tick.

25 · Holds · 9.22 + 9.25

One object, three faces

A hold takes away access a role still grants, without touching the role. It is the same object the member reads as “withheld” in §20 — authored on the row it holds, listed under Review, and chased once its review date passes. The API calls it an allowance; the interface does not, because the word reads as permission granted when the object withholds.

26 · The member side, with two add-ons

A share is a place. A door is not.

TrueNAS earns a destination because there is something to look at and a password to set. Unifi Access does not: a door is something you walk through, so it lives under the role that opens it, and the card is one line of status because an operator enrols it, not the member.

27 · Taking access away on a target · 6.17

The sentence the endpoint exists to make you read

A revocation on an add-on cannot end a session that is already open. The backend fixes that copy and refuses the call without a confirmation, so the dialog's whole job is to put it in front of somebody before they believe the door is shut. It reads as a revocation, so it is dressed as one — the same type-to-confirm and the one solid red fill in the product, from §14.

28 · Door cards

Somebody has to hand over a piece of plastic

A card is enrolled by an operator standing next to the person, so it lives on the person's page, and every card issued is listed on the Unifi Access page for when one turns up in a drawer. The member only ever reads its status — see §26.

29 · Dormant accounts · 9.11–9.12

Accounts nothing points at any more

An account Syndra created whose reason for existing has gone — the person left, the role was deleted, or the mapping changed. This is the one list in the product with a bulk action, and it is allowed here for a reason worth stating: no active role grants any of these, so removing them takes access away from nobody. Where a bulk revoke would be guessing at forty people, this is tidying forty things that already grant nothing.

The listing endpoint this needs

Not built. Dormancy is a judgement the backend has to make, not a filter the frontend can apply — it needs the reason, and it must exclude anything an active role still grants.

GET /api/v1/targets/{target}/accounts/dormant
→ {
  state_read_at, truncated,
  accounts: [{
    account, subject_id | null, display_name,
    reason: "membership_ended" | "role_deleted"
        | "mapping_removed" | "never_assigned",
    subject_still_member: bool,
    last_seen_at, bytes_held
  }]
}

truncated and state_read_at for the same reasons as everywhere else. bytes_held is what makes the acknowledgement above possible.

30 · Connecting to it · 10.8

The last two feet

A member with an account, a password and a path still cannot open a folder. This sits at the bottom of §20, below the credential form, and appears only once an account exists — instructions for connecting to something that has not been created are just a way to make somebody feel stupid.

Only what entitlements reach, today

The list is generated from GET /me/targets, never from a template. A path in here that does not work teaches a member to distrust the whole page, and the next thing they distrust is the part that was right.

Absent in two of the three states

No entitlement and no-account-yet both render without this block — same rule as the credential form in §20. There is nothing to connect to, and saying otherwise is the failure that page is built to avoid.

The host name is deployment configuration

nas.local comes from the add-on's registration, like its nav row in §19. Nothing here is typed into the frontend, so moving the NAS does not mean editing a component.

No instructions for doors

Unifi Access has nothing to connect to — you present a card at a reader. Its member-side face stays the single status line in §26, which is the whole reason it earns no destination of its own.

31 · Three patterns, used everywhere

Decide once, not per screen

Three questions came up on nearly every add-on screen: how old is what I am looking at, how urgently does this need to happen, and how hard should it be to agree to. Each was answered separately as it arose, which is how a product ends up with four kinds of the same thing. Here they are as one component and two rules — everything in §19–§30 is retrofitted to them, and anything new should reach for these rather than invent a fourth.

32 · Motion

Softness without delay

Hover the row, button, tab, nav and disclosure specimens; the three that model a page loading — list arrival, dialog, changed-under-you — play once on entry and replay from the button above them. Six durations cover the whole product, and nothing on the critical path is slower than 260ms, because an operator clearing a queue of twelve should never wait for the interface. Motion here does three jobs and no others: it softens the arrival of things you did not ask for, it confirms the thing you touched, and it marks the one state that is still changing.

Direction carries meaning

Things the system produced rise — rows, panels, results. Things you opened scale from where you clicked. Nothing slides sideways; nothing ever moves more than 10px.

Only one thing loops

A repeating animation means this is still happening. Degraded mode breathes and loading shimmers. Nothing healthy, and no decoration, is ever allowed to loop.

Never on a number

Counts, dates and ids do not animate into place — they are read, not watched. What animates is the row around them, once, when the value arrived while you were looking elsewhere.

Under prefers-reduced-motion every duration collapses to zero and every loop stops. No state is conveyed by movement alone, so nothing is lost — the amber pool still turns amber, the row still tints, the dialog still appears.

What deliberately does not move

Page transitions between routes — the sidebar and header are persistent, so crossfading the content area would imply a bigger change than happened. Table sorting and filtering — rows reorder instantly, because animated reordering makes it impossible to follow one row with your eye. Counts and timestamps. Anything in a confirmation dialog after it has opened. And the healthy state, which earns its calm by being the only thing on screen holding perfectly still.

Open questions

Labels are settled

Basic / Advanced, per your call. The alternatives considered are kept in §02 for the record.

Acknowledged expiry

Nothing here fakes "I'm deliberately letting this lapse." If operators ask for it, it's a real state with its own column and endpoint — flagging, not assuming.

Bulk revoke

S6 offers bulk adopt and bulk mark-as-external but no bulk revoke, on purpose. If your triage backlog is routinely twelve deep, that decision is worth revisiting together.
