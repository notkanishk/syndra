# Feature Coverage Matrix (Planned vs Integrated)

> **Navigation:** See [INDEX.md](../../../INDEX.md) for the full spec graph. See [ROADMAP.md](../ROADMAP.md) for phase timeline.

Last updated: 2026-07-07 (wave-2-part-4-zitadel-state-projection-and-drift-control)

This document compares the **initially planned** Syndra feature surface (as described in `openspec/changes/syndra-core-architecture/design.md`) against what is **already integrated in the repo** (backend + UI). It is meant to be a durable “reality check” that future specs/design changes can reference.

Phase 3 is fully complete. Phase 4 is in progress: Provisioning Intents, Shadow Password Vault, and Sync Service are Integrated. Remaining Phase 4 item: LLDAP Integration (end-to-end wiring, reconciliation loop, and validation against the real external LLDAP deployment). That work is currently paused while Syndra researches whether the current shadow-password propagation model is actually compatible with LLDAP. Phase 5 is in progress: Grant Expiration Scheduler and Live Zitadel Data Source are Integrated; other automation, reconciliation, bulk ops, rate limiting, observability, and CI/CD items remain ahead.

Legend:
- **Integrated**: present end-to-end (API/storage + UI where applicable) or otherwise usable in the intended flow.
- **Partial**: present but stubbed, dev-only, or missing a major part of the intended design.
- **Not integrated**: described in the design, but no meaningful repo support found yet.

## Practical takeaways (what this matrix implies)

- The repo reflects a **hardened Phase 3 baseline**: seeded demo catalog + governance workflows + topology graph + cache/action simulation + Phase 2 contract hardening + full Phase 3 security boundary (backend JWT auth, HMAC webhooks, idempotent onboarding, and frontend OIDC token forwarding).
- For a detailed timeline of future implementation steps, see `openspec/changes/syndra-core-architecture/ROADMAP.md`.
- Phase 3 is fully closed. The zero-trust backend-vs-UI path is Integrated: the frontend performs PKCE OIDC login, stores and forwards Zitadel-issued access tokens, and the SSR helper (`resolveAuthToken` in `ui/src/lib/api.ts`) enforces this by throwing rather than silently falling back to the API key in OIDC mode. Role management is Integrated with Snapshot & Fork cloning and a global role catalog.
- Remaining gaps before full production readiness fall into two categories:
  - **Phase 4 (Infrastructure Bridge):** LLDAP end-to-end integration and password-sync compatibility research.
  - **Phase 5 (Automation & Governance):** Grant expiration enforcement is now Integrated (see `backend/internal/services/expiry/`). Zitadel-side reconciliation is now Integrated (drift detection + triage + cascade projection, Wave 2 · Part 4 — see `drift-control` above). Remaining items: LLDAP reconciliation loop, compensating revocations on partial failure, welcome bundle configuration UI, service-to-bundle mapping, rate limiting, observability, disaster recovery, and CI/CD. See [operational-readiness spec](operational-readiness/spec.md) and the [Roadmap](../ROADMAP.md) for the full list.
- Some design bullets are implemented by **equivalent behavior** (e.g., topology UI uses a lane-based SVG renderer rather than React Flow).

## Immediate next step

Phase 4 is in progress. Provisioning Intents, Shadow Password Vault, and Sync Service are complete at the code level. The next step for the LLDAP bridge is research and compatibility validation against the real external LLDAP deployment before resuming end-to-end integration work.

Phase 5 has started with the Grant Expiration Scheduler. With Phase 4's LLDAP work paused on external research, the next unblocked Phase 5 candidate is **Partial Failure Rollback** (compensating revocations in `EnforceMappingRules`/`RevokeMappingRules` when Zitadel API calls partially fail) — it tightens the same best-effort compromise the scheduler inherits.
