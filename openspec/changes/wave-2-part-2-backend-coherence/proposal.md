# Wave 2 · Part 2 — Backend Coherence

**Status:** Proposed
**Source:** [May 2026 audit resolution design](../../../docs/superpowers/specs/2026-05-08-may-2026-audit-resolution-design.md) §3 Theme 3 — audit refs **B3, B5, B7, C4, C5, B6/C11/D8**
**Phase:** 5.5
**Wave:** 2 (Part 2 of 4 — backend internal seams before drift control; Parts 1, 3, 4 cover frontend palette, operational polish, and drift control)

## Why

The May 2026 audit found six internal-seam findings in the Go backend that, individually, are tolerable but together impose a real coordination tax: every request re-walks state that another request just walked, every operator login parses the same JWT twice, every webhook decodes a payload through three layered fallthroughs whose silent defaults are indistinguishable from genuine inputs, and a 1303-line `repositories.go` file forces every contributor to re-orient through nine domains worth of unrelated queries before reaching the one they came for. None of these are user-visible defects — they erode contributor velocity and obscure the substrate that Wave 2 · Part 4 (Theme 2 — drift control) will build on.

This wave is the cleanup pass that hands Theme 2 a coherent backend. The audit's traceability table marks Theme 3 as a hard prerequisite for the drift-control rollout: `services/views.go` is the file the new projection lookups will sit beside, and Theme 2 cannot land on a 797-line file whose role-resolution helper is invoked N times per request before the new projections add another N. The split must happen now; not later, and not interleaved with new behavior.

## What changes

- **Request-scoped access snapshot in `services/views.go` (B3).** The current `collectUserRoles(ctx, userID)` helper is invoked once per `(user × view)` combination — `ListUsers` calls it N times, `ListApplications` calls it N×M times (per user × per app), `ListProjects` calls it N×P times. A new request-scoped `accessSnapshot` value type lazily computes-and-memoises the role map per user; `ListUsers`, `ListApplications`, `ListProjects`, `Topology`, and `BundleImpact` thread the same snapshot through one read per user. The file shrinks from 797 to ~520 lines and the worst-case query fan-out for `/api/v1/applications` drops from O(N·M) to O(N).
- **`internal/db/repositories.go` split (B5).** The 1303-line file is split into 11 domain files inside the same `db` package: `bundles.go`, `rules.go`, `audit.go`, `grants.go`, `access_requests.go`, `claim_profiles.go`, `onboarding.go`, `webhooks.go` (covers events + grant index — both webhook-maintained), `roles.go`, `intents.go`, and `vault.go`. Function bodies and exported names are unchanged; no callers move. The audit's enumerated list (9 files) becomes 11 because the access-requests, claim-profiles, and grants-index sections are recognised as distinct domains during execution — rationale documented in `design.md`.
- **JWT principal in request context (C4).** `auth.ValidateToken` is widened to `auth.Validate(ctx, token, domain, audience) (*Principal, error)`, where `Principal` carries `Subject string` and `ProjectRoles map[string]struct{}`. `withUserAuth` parses once and stashes the `*Principal` in `r.Context()`; `withOperatorAuth` reads it back via `principalFromContext(ctx).HasProjectRole(adminRoleKey)`. The standalone `auth.HasProjectRole(rawToken, roleKey)` function — which does its own base64 + JSON unmarshal of the JWT payload — is deleted. Each operator request now parses the JWT exactly once instead of twice.
- **Redis-backed `claim_failure_mode` read-through cache (C5).** A new helper `claimFailureModeRead(ctx, projectID)` in `handlers/action.go` reads `claim_mode:<projectID>` from Redis first, falls back to `db.GetClaimFailureMode`, and writes-back on DB success with a 5-minute TTL. On transient DB error the helper returns the cached value (if any) instead of silently defaulting to `fail_closed` — which today masks DB outages as policy decisions. `db.GetClaimFailureMode` itself is unchanged and stays the source of truth. The cache key lives next to `mapping:<userID>:<projectID>` (the existing claim payload key) per the audit's "next to the claim payload" instruction.
- **Strict webhook validation for missing `event_type` (B6).** The silent fallthrough at `webhook.go:77-79` (`event.EventType == "" → "grant_added"`) is removed. Internal-shape callers (operator curl, contract tests) with a missing `event_type` now receive a structured `400 VALIDATION_FAILED` payload, identical in shape to the existing missing-`user_id` and missing-`source_project` responses. Zitadel-shape callers are unaffected — `translateZitadelEvent` resolves the event type before the strict check, and the existing line 60-64 200-ack for unknown Zitadel events still prevents redelivery storms.
- **Observable enrichment-incomplete acknowledgement (C11/D8).** The `webhook.go:104-109` 200-ack for Zitadel-shape grant events with unresolvable enrichment stays in place — it is the documented storm-prevention path — but the outcome becomes observable: the event is persisted to `webhook_events` with status `dropped_enrichment_incomplete` (a new enum value) so operators can query "how many grant events are silently dropping" without scraping stdout. This is the "tighten silent defaults" intent of the audit applied without re-introducing the redelivery storm risk that the original 200-ack was added to prevent.
- **Typed `ErrComplexity` sentinel in `services/vault.go` (B7).** `ValidatePasswordComplexity` returns errors wrapped with a new `services.ErrComplexity` sentinel (`var ErrComplexity = errors.New("password complexity")`). `handlers/vault.go` replaces the `len(err.Error()) > 20 && err.Error()[:20] == "password complexity:"` prefix-sniff with `errors.Is(err, services.ErrComplexity)`. The `isComplexityError` helper is deleted.
- **Spec deltas.** Two capabilities receive added scenarios (no existing requirements modified):
  - `application-claims/spec.md` — Redis-cached degraded-mode fallback survives transient DB outages.
  - `lifecycle-event-propagation/spec.md` — Internal-shape `event_type` strictness + structured `dropped_enrichment_incomplete` outcome.
- **Regression coverage.** New tests cover: (a) `ListApplications` and `ListProjects` issuing one role-resolution call per user instead of N × M / N × P; (b) `withOperatorAuth` reading from context without re-extracting the bearer token; (c) Redis cache return on simulated DB error; (d) `event_type=""` → 400 for internal-shape callers; (e) `errors.Is(err, services.ErrComplexity)` round-trips through the handler.

## Out of scope

- **Theme 2 (Wave 2 Part 4)** — drift control architecture, outbox table, drift triage UI, per-rule `confirmation_mode` flag.
- **Theme 5 (Wave 2 Part 3)** — operational polish (`mapping_rules.version` drop, sync env wiring, scripts dedup, `grantLookupMaxPages`, smoke-test paths, LDAP empty-DN placeholder). Theme 3 leaves `rule.Version` references intact in `views.go:Topology` and `models.MappingRule`; Theme 5 removes them.
- **Theme 1 (Wave 1)** — already shipped: signing-key strict mode, OIDC profile fetch, welcome-bundle explicit flag, vault dev-mode actor, `cmd/test/main.go` deletion.
- **Theme 4 (Wave 2 Part 1 + Wave 3)** — frontend. Part 1 (palette finalization) has shipped; the remainder (useNameResolver trim, `lib/api.ts` dead exports, `app/zitadel/page.tsx` split, ⌘K strike, `location` drop, middleware/proxy tests) is Wave 3.
- **Behavior change in `degradedResponse`.** The cache is a fallback path on DB error only — the steady-state DB read is unchanged. `fail_closed` remains the safe default when no cache and no DB row exist.
- **Webhook redelivery semantics.** The 200-ack at line 104-109 stays; only its observability changes. This deviation from a literal reading of the audit's "returns 400" wording is documented in `design.md` Decision 5.
- **OpenSpec `syndra-core-architecture` design.md edits.** Cross-cutting docs (CLAUDE.md, ROADMAP.md, INDEX.md) are owned by Theme 2 per the audit-resolution design's §7 table; Theme 3 touches only its own scope.
