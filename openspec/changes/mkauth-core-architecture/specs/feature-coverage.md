# Feature Coverage Matrix (Planned vs Integrated)

Last updated: 2026-04-14

This document compares the **initially planned** MkAuth feature surface (as described in `openspec/changes/mkauth-core-architecture/design.md`) against what is **already integrated in the repo** (backend + UI). It is meant to be a durable “reality check” that future specs/design changes can reference.

Phase 3 backend controls are implemented: backend user-token authorization (`withUserAuth` + `auth.ValidateToken`), production data-plane security (50 ms Redis timeout, `claim_failure_mode`, explicit `degradedResponse`), webhook authenticity (HMAC-SHA256 over timestamp+body + 5-minute freshness window), and backend-owned onboarding infrastructure (`onboarding_triggers` table, `TriggerOnboarding` service). Phase 3 is still **in progress** — the zero-trust backend-vs-UI requirement remains Partial until the frontend OIDC login flow forwards Zitadel-issued tokens to the backend. After that, the next priorities are the Zitadel Management API client (M2M) and the full LLDAP infrastructure bridge (Phase 4).

Legend:
- **Integrated**: present end-to-end (API/storage + UI where applicable) or otherwise usable in the intended flow.
- **Partial**: present but stubbed, dev-only, or missing a major part of the intended design.
- **Not integrated**: described in the design, but no meaningful repo support found yet.

## Practical takeaways (what this matrix implies)

- The repo reflects a **hardened v1 baseline**: seeded demo catalog + governance workflows + topology graph + cache/action simulation + Phase 2 contract hardening + Phase 3 backend security controls.
- For a detailed timeline of future implementation steps, see `openspec/changes/mkauth-core-architecture/ROADMAP.md`.
- Phase 3 backend controls are complete (Zitadel JWT auth, HMAC-verified webhooks, explicit data-plane degraded behavior, idempotent onboarding infrastructure), but Phase 3 is not fully closed: live Zitadel OIDC login in the UI (token forwarding to backend) is still missing, keeping the zero-trust backend-vs-UI path Partial.
- Remaining gaps before full production readiness: UI OIDC token forwarding (completes Phase 3), Zitadel Management API M2M client, and the LLDAP infrastructure bridge (Phase 4).
- Some design bullets are implemented by **equivalent behavior** (e.g., topology UI uses a lane-based SVG renderer rather than React Flow).

## Immediate next step

Wire the frontend OIDC login flow to forward Zitadel-issued user tokens to the backend (`Authorization: Bearer <jwt>`), replacing the demo session auth for the admin-facing routes. This closes the last gap in the zero-trust backend-vs-UI requirement.
