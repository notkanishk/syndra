TrueNAS facts are from the public middleware source at tag `TS-25.10.7` (`src/middlewared/middlewared/…`), read by a scout this session; runtime behaviour was not exercised anywhere. ## 0. The answer in one screen

| # | Decision | Why |
|---|---|---|

## 1. What TrueNAS `user.delete` actually does (TS-25.10.7)

Source: `plugins/account.py:1017-1110` (`do_delete`), `api/v25_10_0/user.py:246` (`UserDeleteOptions`).

1. **Options.** `UserDeleteOptions { delete_group: bool = True }` — the only option. The add-on sends `[id]` with no options (`operations.go:580`), i.e. the default, implicit. Pin it explicitly (determinism).
2. **Order of `do_delete`.** Refuse directory-service users (EPERM) → `audit_callback(username)` → refuse "currently active user" **only for user sessions** (an API-key session is not one, so the self guard in `operations.go:418-426` is Syndra's, not TrueNAS's) → refuse `builtin` → refuse `immutable` → `privilege.before_user_delete` (refuses the last local `FULL_ADMIN`) → **primary group**: if `delete_group` and the group is not builtin and has no other members and is nobody else's primary, `group.delete` (a failure is logged and swallowed) → **home**: `shutil.rmtree(home/.ssh)` only, when `home != DEFAULT_HOME_PATH`; the folder and every file stay, owned by the bare uid; there is no option to remove the home → `smb.remove_passdb_user` if `smb` → guest reset if it was this user → webui attribute row deleted → datastore delete → reload ssh, `reset_tally`, reload user, idmap gencache entry removed.
3. **Not touched:** API keys of the user (shown as `revoked, "User does not exist"`, not deleted); **user quota rows** on datasets (Syndra sets one keyed by uid, `home.go:142-143`) — they survive keyed by the dead uid and would apply to whoever next holds it; **share ACL SIDs** (`share_info.tdb`, `smb.sharesec` is private) and **filesystem ACL/owner entries** anywhere on the pool — orphan uid/SID.
4. **Locked users can be deleted** (no `locked` check). So "off before delete" is Syndra's rule to enforce.
5. **uid reuse.** `user.get_next_uid` (`account.py:1253`): lowest gap in `range(MIN_AUTO_XID, max_uid)` over DB rows and in-flight reservations only; file ownership is ignored. A purged Syndra uid (200000+) becomes a gap; it is handed out only once every number below it is taken, i.e. in practice to an admin who types it, not to auto-allocation. Defence in depth, not the main guard.
6. **Roles.** `user.delete` is registered under `ACCOUNT_WRITE` (`main.py` CRUD registration, `user` service has no `role_separate_delete`; `role.py:24-25` has no `ACCOUNT_DELETE`). `pool.snapshot.create/hold` need `SNAPSHOT_WRITE`, `pool.snapshot.delete` needs the separate `SNAPSHOT_DELETE` (`plugins/pool_/snapshot.py:15`, `role.py:207-210`). `filesystem.chown/setperm/setacl` need `FILESYSTEM_ATTRS_WRITE` and are audited with the path (`plugins/filesystem_/acl.py:154,211,634`). `filesystem.statfs(path).source` names the dataset holding a path (`FILESYSTEM_ATTRS_READ`). There is **no API that finds files by owner**; a scan would walk `listdir`. `user.delete` is audited (`audit='Delete user'`, callback runs before the checks, so refusals are audited too); `pool.snapshot.*` is **not**.
7. **Disabling.** `user.update {locked, password_disabled, smb, ssh_password_enabled, shell, sudo_commands}`; `locked` rewrites the passdb entry with `AUTO_LOCKED`, `smb:false` removes it; no account-expiry field at 25.10. Syndra's lifecycle "off" is `locked` set + `smb` cleared (`addon-platform/design.md:254`, `apply.go:1028,1243`).

**Discrepancies to fix regardless of this work:**
- `handlers/inventory.go:426-430` and `dormant.go` comments say the add-on "cannot remove one". False; `.env.example:200-206` and `DEPLOY.md:934-940` have the correct statement. Comment drift.
- Registry says "Remove a **disabled** account" (`contract/v2/registry/operations.json:22`) and the kit purges only an account that is off (`conformance/mutate.go:339-340`), but `purgeAccount` (`operations.go:539-600`) never checks `locked`. The rule exists in prose and a test, not in the gate.

## 2. The uid-reuse hazard

**How others handle it.** Windows/AD never reuses a RID and keeps a tombstone for `tombstoneLifetime` (default 180 days); Entra ID soft-deletes users for 30 days; Google Workspace restores a deleted user for 20 days; FreeIPA `ipa user-del --preserve` keeps the entry as preserved **(all known; verify)**. POSIX `userdel(8)` warns in its own man page: "You should manually check all file systems to ensure that no files remain owned by this user" — the tool itself admits the orphan-uid problem and pushes it to the operator (`find / -nouser`). NIST SP 800-53r5 IA-4(d): prevent reuse of identifiers for a defined period **(known)**.

**What Syndra can do, and what I recommend (D1 + D5):**

| Option | Verdict |
|---|---|
| High-water mark (`ClaimID`, `store.go:546`) | Already there: Syndra never hands a number out twice, as uid and gid together (`identity.go:44-75`). Keep. Covers Syndra-made accounts; not a hand-made account given a dead number by an admin. |
| Tombstone record | **Yes.** Cheap, one bucket, append-only; makes the dead number a *known* number: a `/subjects` row whose uid is tombstoned and whose name is not the tombstone's name is a finding (`binding_conflict`'s sibling, or the same row with reason `dead_number`). It is the memory that lets 7t's rule "in-range uid names its account by number" stay true after deletes. |
| Re-own the home (`filesystem.chown` uid 0, gid = admin group, recursive; `setperm 700`) | **Yes, always, before `user.delete`.** Reversible from the record (old uid in the mutation log and the tombstone). Removes the hazard at its root for the one tree Syndra knows about. Fails closed: a chown that fails refuses the purge and nothing is deleted. |
| Refuse while files remain elsewhere | **No.** There is no API to find them; a `listdir` walk of every share is minutes of reads on a NAS with members on it, and still cannot see ACL entries. Document it: files outside the home keep the dead uid; Syndra never reuses it; the operator may run `find -nouser` on the NAS outside Syndra. |
| Delete the home | **Not in this slice.** Owner's open policy (keep / archive / delete after N days). No public `filesystem` method removes a tree at 25.10 (**UNVERIFIED**: `filesystem.get/put` are `FULL_ADMIN`; I saw no `filesystem.rmtree`); if it needs a shell, it is not the add-on's to do. |

## 3. Safety and determinism, item by item

**3.1 Two-phase delete.** On → off is the lifecycle today: departure auto-send (§37) or losing the last role sets `locked` + clears `smb`, and the hold on a person (Syndra lifecycle hold) keeps the account entitled so it never lists as dormant (`dormant.go:144-152`). New: **`off_since`** on the add-on's binding, written in the same `mutate` as the `user.update` that locks (one write place, the component that knows the target's state), cleared when unlocked, reported per row on `/subjects`; adoption of an already-locked account sets it to the adoption time (conservative). The backend refuses a purge of a row whose `off_since` is younger than the per-system hold (setting `purge_hold_days`, default 30 — the Entra/Google order of magnitude; NIST AC-2(3) leaves the period to the organisation). Rows inside the hold are shown with the date they become removable, not hidden.

**3.2 Preview.** The dormant list *is* the preview today, but it says nothing about files, groups, snapshots or the number. Per D4 the backend sends `account.purge` with `preview: true` per listed row (or the add-on answers it inside `/subjects`, cheaper — owner Q7) and shows: account name and number, off since, home path, home bytes (`pool.dataset.get_quota` USER row `used`, already read for `storage.status`), what happens to it ("kept, private to makerspace staff"), personal group (deleted / kept because others are in it), latest snapshot of the home's dataset and its age (`filesystem.statfs(home).source` → `pool.snapshot.query` newest; `SNAPSHOT_READ` on the standing key), and any reason it would be refused (not off, inside hold, conflict). Preview writes nothing — not even a mutation-log record (AUTHORING physical rule 1).

**3.3 Exact-target confirmation.** The plan gate issues `plan_id` for surface `accounts.purge` with one row per account and a fingerprint `(target, subject, account_id, username, off_since, state_read_at)`; the sweep cites it and the gate refuses a changed fingerprint the way it refuses every other surface (`plan_gate.go:28-31`; memory: all surfaces in one list). Independently, the add-on's confirm carries `expect: {account_id, username}` and `operatedAccount` must return *that* account — 409 on any conflict (`claimed_twice`, `ambiguous`, legacy halt), 422 `TARGET_CHANGED` on a rename or a different number, 422 `ACCOUNT_NOT_OFF` when `locked` is false or `smb` is true, 422 when self (`refuseSelfAccount`), 422 when no binding (never an account Syndra did not create or adopt). Writes happen under the per-subject lock (calls.go rule 5) so resolve-then-act is one critical section.

**3.4 Idempotency, WAL, settle.** `call_id` is the dedupe key (AUTHORING "every write once per call_id"); every step is its own `mutate` under that call (`apply.go:1474-1500`: intent fsynced, write, result). Steps, in this order, each a no-op when already done:
1. `filesystem.chown {path: home, uid: 0, gid: <admin>, options: {recursive: true, traverse: false}}` (a job; wait for it)
2. `filesystem.setperm {path: home, mode: "700"}` (only if not already 700)
3. `pool.dataset.set_quota [dataset, [{quota_type: USER, id: uid, quota_value: 0}]]` (only when a row exists)
4. `user.delete [id, {delete_group: true}]` — on the elevated session, `callOnce` (as today)
5. `store.tombstone` then `store.unbind`
Steps 1-3 are harmless if 4 never happens; 4 is the only one that cannot be undone, and it is last. An answer lost at step 4 leaves the intent open → `/calls` answers `in_doubt` → the backend's `settleByCall` (`handlers/unconfirmed.go:132`) reads the target: account gone ⇒ `done`, run steps 5 only; account present ⇒ `not done`, the operator may send again with a new `call_id`. RFC 9110 §9.2.2 makes DELETE idempotent; the Idempotency-Key draft (draft-ietf-httpapi-idempotency-key-header) is the same shape as `call_id` **(known)**.

**3.5 Authorisation.** Operator (admin, `withOperatorAuth`) + the typed elevated key (D8) + the acknowledgement that names the data (`AcknowledgeCount`, `DormantAccounts.tsx:227-262`). NIST AC-5 separation of duties cannot be met by one person; AC-2(4) (automatically audit creation, modification, disabling, removal) is met by the rows below. The key's lifetime: minted for the session, deleted after (DEPLOY.md:942-945); consider a Syndra-side check that the key's TrueNAS user is `syndra-purge`, not the standing user (`auth.me` on the elevated session, one read).

**3.6 Audit trail** (exists; extend): backend `addon_operations` record + audit row before the call (`dispatch.go:286-304`); add-on mutation log, hash-chained (`mutationlog.go:700-712`), one intent/result per step; TrueNAS's own audit (`Delete user <name>` by user `syndra-purge`, `Filesystem change owner <path>`); the tombstone. The person's audit page shows "a delete of an account" (`audit-vocabulary.ts:197`), destructive tone. Add the home's fate and the number to the audit detail so the record answers "where are the files" without the log.

**3.7 Recoverability.** D6: read the snapshot age and say it; do not take or hold one. If the owner wants a Syndra-taken snapshot anyway: `pool.snapshot.create {dataset, name: "syndra-purge-<uid>-<call_id>"}` with `SNAPSHOT_WRITE`, no `hold`, retention left to the NAS, and the add-on records it in the tombstone; it needs the purge key to carry `SNAPSHOT_WRITE` and the preview to say the snapshot is dataset-wide. Account recovery itself: an apply for the subject (if they return) creates a **new** account with a **new** number and an empty home (`home.go:24-25` refuses a folder owned by another uid — the archived one is root's, so it is refused and the outcome says where); staff hand the old files back by hand. Say this in the preview.

**3.8 Blast radius.** One account per add-on call (today); the sweep's request names an explicit list (`inventory.go:421-425`); cap one sweep at, say, 20 rows (owner Q9). Never: self, builtin/immutable/directory users (TrueNAS), out-of-range unless adopted-with-marker (resolver), unbound, entitled, held, inside the hold, not off, conflicted, or a fingerprint that moved.

## 4. Product flow

- **Where.** The system's page › "No longer needed" (Basic): rows grouped by reason as today; each row gains *off since*, *removable from <date>* (or the Remove checkbox), *folder: 2.3 GB, kept private to makerspace staff* (or *no folder*). Advanced: uid/gid, home path, dataset, latest snapshot age, plan id. Nothing on `TargetOverview`'s operations list changes except the label stays "Deletes an account" (`TargetOverview.tsx:997`).
- **Copy** (copy guide: delete = object ceases to exist → purge, `plain-language-copy/design.md:508`; the label names no system, `:911`). Acknowledgement: "I understand this deletes {n} accounts on {system}. Their folders stay, and only makerspace staff can open them." Result per row: "Deleted. The folder is kept, private to makerspace staff." Refusals: "Still on — Syndra deletes only accounts that are off." / "Off since 3 Nov; can be deleted from 3 Dec." / "{system} changed this account since you read the list. Read it again." Unconfirmed: existing wording in `UnconfirmedChanges.tsx:93-100` stays.
- **Person page** (read-only, one write place): "Account on TrueNAS: off since 3 Nov. Can be deleted from TrueNAS's page after 3 Dec →". After a purge: "No account on TrueNAS. The folder from before is kept by makerspace staff."
- **Departure → delete.** Auto-send locks (§37) → `off_since` set → after the hold the row appears removable → operator removes. **No auto-purge** (`addon-platform/design.md:255-256`, stays). A Syndra hold keeps the account entitled, so held people never appear (`dormant.go:150`).
- **Member sees** nothing new: sign-in already fails since the lock. On return: a fresh account, fresh folder, and a line from staff about the old files.

## 5. The contract (generic)

`POST /operations/account.purge` — params `elevated_key` (secret), `expect {account_id, username}` (required on confirm; optional on preview); `preview: true` without `call_id` answers what the confirm would, writing nothing. Reply `result` (new `common/purge.json`): `{account_id, username, off_since, home: {path, bytes|null, after: "kept_private"|"kept"|"none"}, group: {deleted: bool, reason}, snapshot: {latest_at|null, dataset}, writes: [...]}`; on confirm the same shape with `writes[].outcome`, plus `consequence` ("Deleted. The folder is kept, private to makerspace staff."). `/subjects` rows gain `off_since`; the document gains `tombstones[] {account_id, username, subject, at}`. Refusal codes: `ACCOUNT_NOT_OFF`, `TARGET_CHANGED`, `BINDING_CONFLICT` (exists), `BAD_REQUEST` for preview with `call_id`.

Guarantees any add-on must give (AUTHORING §7 "Deleting an account"): refuse unless the account is off on the target; refuse unless `expect` matches the account the binding resolves to now; never hand the identifier out again (kit `identity.not-reused`, `report.go:42`, stays advisory for apps that recycle ids, with the tombstone as the compensating control); leave nothing in the account's own space owned by the dead identifier (re-own or report `home.after = "kept"` with the warning); at most once per `call_id`, preview = confirm checks, `/calls` settles. A Nextcloud add-on would: disable → hold → `files:transfer-ownership` to an admin → delete user; same shape, same report.

## 7. Risks and questions for the owner

1. **Hold length and where "off since" lives.** Recommend 30 days, per-system setting, `off_since` on the add-on's binding (written beside the lock), reported on `/subjects`.
2. **The home after a purge: always re-owned to root, 700?** Recommend yes (D1); it is the 14 Oct shape and the only thing that removes the incident's cause. "Keep as is" leaves the bare uid.
3. **Deleting files after N days** stays a separate change; no public API for it was found (UNVERIFIED). Recommend deciding it after the first real purge.
4. **Snapshots.** Recommend read-and-say only (D6). If you want Syndra to take one: `SNAPSHOT_WRITE` on the purge key, no hold, NAS retention.
5. **Purge key on its own TrueNAS user `syndra-purge`** with `ACCOUNT_WRITE` + `FILESYSTEM_ATTRS_WRITE`; the standing session does the reads. Recommend yes; it makes the NAS audit log tell the two apart.
6. **`effect: "physical"` for `account.purge`** (reuse preview/confirm/`/calls`) vs a new flag. Recommend reusing `physical`; one pipeline.
7. **Preview per row via `preview: true`, or the facts in `/subjects`?** Recommend `/subjects` carries `off_since` and home bytes (both cheap, both useful elsewhere) and the per-row preview is sent only when the operator opens the row.
8. **Plan-gate surface `accounts.purge`** in addition to the add-on's `expect`. Recommend yes; it is the project's one way of binding two requests.
9. **Cap per sweep** (recommend 20) and whether the generic operation endpoint should refuse `account.purge` (recommend yes, D7).
10. **Fix the two drifts first** (comment "cannot remove one"; no off-check in `purgeAccount`) in a small PR before any of this.
11. **Orphan uid outside the home** (shared folders, share ACL SIDs): accepted, documented, uid never reused by Syndra; an occasional `find -nouser` on the NAS is yours.
12. **The `delete_group: true` default**: keep, but send it explicitly; when TrueNAS keeps the group (others in it), say so in the result.
