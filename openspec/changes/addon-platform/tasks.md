- [x] 1.10 Thread `target` through the propagation claim, drain, and terminal-state writes in `services/propagation`; the drain claims one target per pass and skips targets whose registry state is not `active`. Both conditions live in the claim, not in the drain: the function is exported, and an invariant a caller enforces is one the next caller can skip. This was not cosmetic — the moment a second target registers, the existing drain would claim its rows and push them through the Management API path, where a TrueNAS row has no project and no roles to send. The row carries its `target` so the drain can see what it is holding, and `FOR UPDATE OF p` locks the outbox rows only: locking the `targets` row it joined for the state check would serialise every drain against every registry write. A pass reports the active targets it did **not** dispatch, because a drain that emptied one queue while another waits is otherwise indistinguishable from a drain with nothing left to do — and a failure to list them is non-fatal, since the work it did dispatch still happened. Every claim path is scoped, including the ones that name specific rows: `DrainOne` and `DrainBatch` both hand whatever they claim to the Zitadel dispatcher, which would mark an add-on entitlement (`op_type='apply'`) terminally failed as an unknown operation, with no way back from `failed`. Scoping the claim rather than claiming and releasing is the point — releasing costs on every route, and a requeue spends a retry and records a dispatch failure for a dispatch that never happened, so a handful of targeted applies would exhaust an add-on row's budget before its dispatcher exists and its first genuine transient response would halt it. Not claiming costs nothing. A declined claim is explained by a read rather than by a claim: the target is named in `Awaiting`, once per target rather than once per row, and only for rows that are genuinely unresolved on another active target. Add-on targets get their own dispatcher and their own pass in group 4. every terminal-state write is now guarded by `status='in_flight'` and reports a row it did not match as `ErrPropagationNotInFlight`, because deregistration can terminate a claimed row while its dispatch is out — and an unguarded requeue would return that row to `pending` on a target that no longer exists, recreating the undrainable row the deregistration had just resolved, beyond the sweep that already ran. The drain counts these as `Abandoned`: not a failure, since the call may have reached the target, and certainly not a success, since nothing confirmed it

- [x] 1.20 Per-`(subject, target)` serialization and stale-version rejection in the drain. Serialization is already stronger than the requirement and no new mechanism was built for it: the session-level drain advisory lock admits one drain at a time, the background revocation runner shares it rather than taking its own, and within a pass rows are processed sequentially in `intent_seq` order — so two applies for one subject cannot interleave anywhere. Rejection is the new content. `terminateSuperseded` settles an overtaken row **before** the claim, so a stale version is rejected without ever reaching a dispatcher, and it lives inside all three claim paths rather than beside them — the same reason the active-target join is a condition of the claim. The predicate reads the version off the row's own approval chain (outbox → plan subject → snapshot) rather than taking it as an argument, because a version supplied beside a row can describe a decision that never existed; it fires only when a **settled** (`applied`) row for the same `(subject, target)` carries a strictly greater version, since an unsettled later row is not proof the target moved — the drain still dispatches both, in order. Zitadel rows fall out naturally: their plan subject carries no snapshot, so the join drops them, and their ordering is held instead by the claim never inverting a subject's own intent order (1.26)

## 2. Add-on registry and wire contract

- [x] 2.1 Define the manifest types: entitlement schema, operation descriptors (`scope`, `confirm`, `secret_params`), target product and version. The manifest declares no target name — the registration owns it, so there is no mismatch case to resolve. Entitlement fields carry a `lifecycle` flag, the source structural mapping validation needs to reject them (task 7.4)
- [x] 2.2 Add-on registry: config-driven registration (base URL, client-certificate **or** signing-key reference — one transport mode is mandatory and a target with neither does not register at all), manifest fetch and cache, `deps.go` seam for tests. Registration and callability are separate states: `Init` contacts no add-on, so an unreachable one still registers (nav derives from deployment, not from what answers), and a refresh is what turns registration into capability. `Init` does reach the database: it upserts each configured target into the `targets` registry and disables the ones the deployment has dropped, because a target registered only in memory is one whose first snapshot, plan, outbox, or drift row the foreign key refuses. A refused refresh keeps the last accepted manifest rather than revoking a verified capability set
- [x] 2.3 Contract-version check at registration: refuse an add-on declaring a version the backend does not support, with that reason, so a mismatch fails at startup rather than as an absent field later. The version is declared by the manifest, not by backend configuration — a configured copy would only let the backend check itself against itself — so "at startup" is delivered by a synchronous, time-bounded first manifest read before the server accepts anything, not by a config field. It is loud but not fatal: refusing to boot the backend that governs every other target because one add-on shipped ahead of it would invert the fail-open rule. The refusal names both versions, because "the add-on is newer" and "the backend is newer" are different operator actions
- [x] 2.4 Tests: unregistered add-on is not callable; an operation absent from the manifest is rejected even if requested; registered-but-never-answered is a third distinct state rather than either of those
- [x] 2.5 Add-on HTTP client with per-add-on auth, timeouts, and a circuit breaker; carries plan id, fingerprints, and operation id on every mutating call — inside the signed body rather than beside it, so an intercepted call cannot be replayed against a different plan or subject. The callability gate runs before the network and the operation-record id is required before dispatch, so an uncallable operation costs nothing and a mutation cannot outrun its own audit trail. The breaker is per target and ignores deterministic refusals: a 4xx is a healthy add-on saying no, and letting one malformed request open the circuit would turn one operator's mistake into an outage for everyone
- [x] 2.6 Tests: client failure modes — unreachable, timeout, 5xx, open circuit — each map to the intended outcome and never to silent success. Four outcomes, not two, because "did it work" has three honest answers: **succeeded**, **rejected** (it refused and did not act), **unreached** (nothing happened, safe to retry), **indeterminate** (sent, answer lost, may have applied). Only unreached is retryable and indeterminate is neither a success nor a failure — retrying it duplicates a mutation and counting it either way asserts what the backend does not know. A 2xx whose body was truncated is indeterminate too — including one merely too large, since `io.LimitReader` signals its bound with EOF rather than an error and reading exactly the bound cannot tell a body that ended from one that was cut off. An oversized refusal keeps its status-derived outcome and records the truncation: reclassifying a deterministic refusal would turn it into a row that never settles. An already-cancelled context dispatches nothing
- [x] 2.7 Redaction layer keyed off `secret_params`: values stripped before any audit write, log line, or outbox payload. The secret set is resolved from the effective operation — policy ∩ manifest — never taken from the caller, because a caller that forgot to list its secret parameter is exactly the caller whose secret would otherwise be written. It fails closed: an operation that cannot be resolved has every value redacted, not none. `CallRequest` implements `String` and `GoString` so `%v` and `%#v` — the two verbs a future caller reaches for without thinking — cannot print a password; a redaction that depends on every caller remembering to redact is not one
- [x] 2.8 Tests: a secret parameter value never appears in emitted logs or any rendering of the request, asserted by scanning. Covers `String`/`%v`/`%s`/`%#v`/`%+v`, the transport's own failure log, the returned error, nested values, and a manifest that omits a policy-declared secret (policy prevails). Redaction copies rather than mutates, or it would strip the value the caller is about to send. Audit- and outbox-row scanning lands with 2.10/2.12, when there are rows to scan

- [~] 2.19 Apply gate: `internal/services/planapply` refuses an apply citing no plan before it opens anything, then in one transaction reads the target's registration, claims the plan, and queues one row per approved subject. The registration is read under `FOR UPDATE` by the **write itself**, in a locking CTE, not merely by the gate ahead of it — the enqueue is exported, so a lock one caller takes is not an invariant. An unlocked join is an MVCC read: a caller can begin while the target is active, have a deregistration disable it and sweep its queued work, and still commit a fresh row behind that sweep. Under `FOR UPDATE`, READ COMMITTED re-checks the predicate against the version it locked, so a concurrent disable turns into no match; and if the lock is taken first, the disable waits and then abandons what was written. The gate keeps its own lock on the same row for a different reason — refusing before the approval is spent — same row, same order, no deadlock. Serialising is necessary and not sufficient: an apply that wins that race still commits work against a target about to go away, so `DisableUnconfiguredTargets` now resolves what it strands, in the same transaction that changes the state. Stranded rows become `abandoned` — not `failed`, which claims an attempt was made, and not `superseded`, which claims a later decision won — terminated rather than deleted, with the audit row written by the same statement so "terminated" and "recorded as terminated" cannot come apart. ## 4. TrueNAS add-on: skeleton and read path

- [x] 4.1 `addons/truenas`, its own module and its own container. No `ports:` anywhere and no `EXPOSE`: the backend reaches it on the internal network and nothing outside the deployment has any business doing so. Non-root with its own uid, because the state volume holds a mirror naming every account on the target and the mutation log names who did what to whom. Behind the `truenas` Compose profile for a sharper reason than `sync` was — this container holds the NAS API key, so a deployment with no NAS must not be running it at all
- [x] 4.2 One persistent WebSocket behind an `rpc` interface, reconnected on loss, authenticated by API key. The reconnect **cooldown is checked before dialling rather than after failing**, so a burst of calls during an outage costs one login attempt rather than one each — TrueNAS rate-limits authentication to 20 attempts per 60 seconds with a ten-minute lockout, and every operation this add-on performs shares the one session, so a reconnect loop is a way to lock the backend out of its own NAS. A dead socket is dropped rather than reused, or every subsequent call fails on a connection nothing will reopen. Failures are classified into unreachable / refused / rate-limited by string, stated as the compromise it is (the client carries no code) with anything unrecognised falling to **refused** — the conservative direction, since treating an unknown failure as retryable is how a lockout happens. The breaker sits on top: five failed connections open it for eleven minutes — longer than the target's own ten-minute lockout, so a breaker that opened because of one has certainly cleared it before allowing again — and a **rate-limit response opens it at once**, because that is the target saying in as many words that the next attempt is the one that locks the account. A success clears the count outright rather than decrementing it: the failure this guards is a burst, so one working connection means the burst is over, and a breaker that kept its failures would leave the target permanently one hiccup from an outage. Backpressure on a live session counts too, since the next reconnect is what would trip the lockout
- [x] 4.3 Five calls, one login; twenty calls during an outage, one login attempt; a rate limit opening the circuit immediately and holding it past the target's lockout window; ordinary failures opening it at the threshold; a success closing it **and clearing the count**; and health distinguishing an open circuit from an outage, because an operator seeing only "unreachable" looks at the network when what happened is that the add-on backed off
- [x] 4.4 `/health` composes reachability (a real ping, not a cached opinion — that is the field most likely to be wrong exactly when it is read), the target version and whether its major is tested, the API key expiry, the last successful read, the lifecycle state with its in-flight count and whether it has drained, the mutation-log head and record count for the backend to anchor, and the snapshot age. It **degrades per source rather than failing whole**: a 500 because one of five reads failed tells an operator nothing about the other four, which are the ones that would have explained it
- [x] 4.5 An untested major refuses mutations, names the version it saw, and marks every operation unavailable **with a reason** — a disabled button that explains nothing is worse than an absent one. Reads continue: refusing them too would make the backend record the target as unreconciled, which says "we cannot see it" when the truth is "we can see it and will not write to it"
- [x] 4.6 The manifest, served **even while the target is unreachable**: a capability set that vanished during an outage would make the backend withdraw operations that are merely unobservable — the same mistake as concluding an absence from a read that could not happen. `enabled` and `smb_enabled` are declared as lifecycle-flagged entitlement fields, so the backend refuses a role-to-target mapping naming one
- [x] 4.7 `core.get_methods` read once per connection and cached — a fact about a release rather than a moment, and asking per call would spend a round trip through a rate-limited session to learn something that cannot change until the NAS is upgraded. Each operation declares the methods it depends on in one table, so adding an operation without saying what it needs is visible there rather than surfacing as a runtime failure against an older release. An unread method list reads as **everything present**: a target that will not enumerate is not a target with none, and withdrawing the whole surface on one failed read is the same mistake as concluding an absence from a read that could not happen
- [x] 4.8 The full state read, with group ids resolved to **names** — a mapping binds a role to a group name, and comparing a name against a number would make every subject look like drift. A gid with no name is skipped rather than rendered as a number, because it is a group the resolver could never have asked for. `locked` is inverted into `enabled` here, since the backend does not know what TrueNAS calls things
- [x] 4.9 Asserted against a fixture where the NAS **does** return `unixhash` and `smbhash`, which is exactly what it does. Scanned out of the response and out of the persisted snapshot, and the `select` itself asserted not to name them — they are absent by construction rather than stripped afterwards, because stripping is a step somebody can forget and the forgetting would not be visible. The mutation log has no field one could land in, asserted as a closed key list
- [x] 4.10 An operation whose method is missing is unavailable, still declared (omitting it leaves an operator wondering whether the feature exists), and its reason names the method. Unrelated operations stay available, since this is per operation and not per version. An unread method list withdraws nothing. And the untested-major reason outranks the method probe, because "we will not" and "it cannot" are different sentences and only one of them is true on an untested release
- [x] 4.11 bbolt at `0600` — the snapshot names every account on the target. No command queue, deliberately: two durable queues would disagree about what is still pending, and Syndra's is the one that knows why an operation exists. The idempotency retention is the actual replay window and the comment says so; an expired entry is reported absent on the read path and removed by a sweep, because a read that writes turns a replay storm into a write storm
- [x] 4.12 A mirrored read answers, is **not** marked current, and carries its age. Nothing current and nothing remembered is a 503 rather than an empty list: an empty list is a statement that the target holds no accounts, and the drift sweep would act on it. A capped read is reported truncated **and** current, because those say different things — current means the data is fresh, truncated means it cannot support a conclusion about absence, which is half of what the diff does
- [x] 4.13 Append-only JSONL at `0600`, fsynced per record, rotated by size with bounded retention, each record carrying the previous digest. The digest is over a **length-prefixed field list** rather than the marshalled JSON: two encoders ordering keys differently would produce two digests for one record, and a chain that breaks when the writer is upgraded is a chain nobody trusts. A failed fsync fails the Append **and does not advance the head** — a record that may not have survived must not become the link the next one chains onto. Recovery reads the file to the end rather than trusting a sidecar pointer, and a partial trailing line (the shape a crash leaves) is skipped rather than treated as corruption of the whole log
- [x] 4.14 Both on `/health`. The count is the half that detects truncation — a chain alone cannot see it, since deleting the last N records leaves a remainder that verifies perfectly
- [x] 4.15 Durability asserted from disk rather than from the writer, plus the failure path — an fsync that fails refuses the Append, leaves the head where it was, and the next record chains onto the last durable one. Alteration, mid-log removal, and a re-signed edit each break verification with the sequence number named. Truncation is shown to verify cleanly, which is precisely why the anchor exists. A secret-bearing mutation records the event and the record's key set is asserted closed
- [x] 4.16 Three states, none needing a redeploy. `draining` counts what is in flight so "drained" is a fact rather than a guess — that count is what an operator waits on before pulling a credential out from under a call — and the check and the increment share one critical section, or a drain observes zero between a caller being allowed and that caller counting itself. An unrecognised configured value falls to `read_only`, not `active`: an operator who typed `readonly` and got a serving add-on has the opposite of what they asked for
- [x] 4.17 Both states refuse mutations and neither gates a read. Draining reports not-drained while one is in flight and drained once it settles, with `done()` idempotent so a handler that defers it and also calls it on an early return cannot drive the count negative. A 200-goroutine race asserts no drain ever observed itself finished while an allowed mutation was outstanding. The refusal is 503 with `Retry-After` naming the state, which is what the backend reads as queued rather than failed

## 7. Role-to-target mapping and lifecycle

- [x] 7.1 Migration 000029: `target_role_mappings` as the working copy, plus `target_mapping_versions` and `target_mapping_version_entries` as published history — the same working-copy/version split bundles use, and for the same reason: a mapping edit silently changes what every holder of that role can reach. Versioned per **target** rather than per row, because a mapping is only meaningful against the set it sits in and a per-row version would let a rollback restore one binding into a set the rest of which has moved on. Published versions are immutable by trigger: a rollback compares against them, and a record that can be edited is a comparison against nothing
- [x] 7.2 Guards: the binding key includes every dimension **and excludes `value`** — including it would make two values for one field legal, which is the ambiguity the key exists to forbid and a resolver returning whichever the database ordered first; both lookup directions indexed, since both run on the hot path of an access change; versions immutable and per-target; and the rollback refusing while any binding exists, asserted positionally against the DROP. A mapping deleted is a role that silently stops reaching anything, and the resolver would converge every holder to an empty set
- [x] 7.3 Mapping CRUD under `/api/v1/targets/mappings`, with the split validation running **structure first and without a network call**: a field the schema does not declare is wrong whatever the target says, and spending a call to be told so would make an outage look like a validation failure. An edit validates the new value against the mapping's **own** target, since the update body carries none and a value checked against another add-on's schema is checked against nothing. Only the value moves on an edit: re-pointing a mapping at a different role is deleting one binding and creating another, with a different cohort on each side. `GET .../holders` reports the blast radius before anything lands, read from every source of the role rather than from direct grants alone. **Remaining:** the reference half is a seam that accepts every value until the add-on exposes a value oracle (group 4 ships the schema, not the lookup); structure is enforced now

## 17. Wire-contract fixes

The backend and the add-on are separately compiled modules with no shared type,
and each was tested against its own fake. The fakes agreed with each other and
neither agreed with the other binary — the same shape as §13.1, found the same
way: by reading one side's encoder against the other side's decoder.

- [x] 17.1 **Every real `/apply` and `/operations/*` call would have been refused as malformed.** The backend's `applyEnvelope` carries `contract_version`; the add-on's `ApplyRequest` did not declare it and `decodeStrict` refuses unknown fields. The operation leg was worse — `contract_version`, `operation`, `plan_id` and `fingerprint` all travelled and none were declared. Both structs now declare what the backend sends, and every body-carrying route enforces the version rather than merely tolerating it: an absent field reads as version 0, which is exactly what a caller from before the field existed looks like, so it is refused like any other mismatch. The refusal names BOTH versions, because "the add-on is newer" and "the backend is newer" send an operator to different binaries
- [x] 17.2 The operation name travels in the body as well as the path, and a disagreement is refused rather than resolved. In signed mode the MAC covers the request line and the body, so both are authenticated; picking the path would let a body signed for `health.get` drive `account.purge`, and picking the body would let the route an operator authorised be swapped underneath them
- [x] 17.3 The backend sends `actor` on the operation leg. The add-on's `OperationRequest` had the field and the mutation log wrote it — `s.record(op, subject, req.Actor, …)` — and nothing ever populated it, so the one forensic record that survives loss of Syndra's audit tables named only the subject, on the one path that carries a credential
- [x] 17.4 `/plan` takes a `PlanSubject`, not an `ApplyRequest`. A plan has no call id to deduplicate on, no fingerprint to verify against — it is where a fingerprint comes from — and no plan id, because the plan being computed is what will get one. Reusing the apply's shape meant either the backend sending four meaningless fields or the add-on accepting a body it cannot honour
- [x] 17.5 The contract is an artifact both ends are held to: `addons/contract/*.json`, one fully-populated document per envelope. The backend asserts that what it marshals IS that document; the add-on asserts that `decodeStrict` accepts it and that no field decoded to its zero value, since a dropped field passes every downstream check vacuously. Changing one fails two suites in two modules until both ends move
- [x] 17.9 **The lifecycle trigger's decision, and where it hangs.** A cascade-sourced convergence has no operator plan behind it, and the drain refuses a row citing nothing. The system mints its own — `db.RecordSystemConvergence`, on the caller's ambient transaction so the role change and the convergence commit together — and the plan it mints carries `SystemFingerprint` rather than a state digest, because no person reviewed a diff and a fingerprint asserts that they did. The drain re-reads live state for a `entitlements.lifecycle` row before dispatching it. The sentinel is deliberately not digest-shaped, so a code path that stopped re-reading fails closed at the add-on rather than verifying against a value that happened to match. `CreatePlan` gained `beginOrJoin` for the same reason
- [x] 17.10 The trigger hangs off `deltaParams` — the ONE function every closure delta in this package passes through: bundle assign, remove and delete, rule create, update and delete, publish, move-holders, direct-grant removal and expiry. Nine hooks would be nine hooks and one that gets forgotten, and the forgotten one is a person whose access changed in Zitadel and nowhere else. It fires BEFORE the params are built, so a convergence that cannot be queued fails the role change rather than being logged past it. A source guard holds both properties, since an omission is invisible to every behavioural test that does not know to look for it
- [x] 17.11 The drain sends the subject's EMAIL, which it never did. A username is derived from the email localpart once, at creation; without one the add-on's fallback names the account from a digest of the subject id — so every account Syndra created through the drain would have been named `u3f2a9c11` while the plan the operator approved said `ada`. The add-on now refuses to create an account it has no identity to name, rather than inventing one, and the backend resolves the email from the directory at dispatch: the plan store deliberately holds no name or email, and copying identity into it to fix this would have been the wrong repair
- [x] 17.7 **The entitlement spine, which nothing had.** Nothing wrote `desired_state_snapshots` — the table, its immutability trigger and its version allocator existed with no producer — and no route rehearsed or applied an entitlement change, which is why §15.2 records `planapply` and `addonop` as heavily tested and never executed. What lands: `db.WriteDesiredStateSnapshotTx`, `NewPlanSubject.DesiredState` so the snapshot and the plan citing it commit in ONE transaction (a snapshot written first and a plan that then fails is an audit row citing nothing that has already spent a version; the reverse is a citation the drain resolves to nothing and terminally fails an approved change on), `EntitlementSet.Desired()` as the one encoder of the instruction, `services.RehearseEntitlements`, and `POST /api/v1/targets/{target}/entitlements/{rehearse,apply}`. The apply is `planapply.Apply` — its first production caller
- [x] 17.8 **Provisional plans fall out of it** (§2.23–2.27). The add-on's `/plan` now falls back to its mirror rather than refusing, and reports `current` and `taken_at` with the outcomes, so the currency travels WITH the plan instead of being inferred from the target's health a moment later. `!current` makes the plan provisional: no lifetime, gated by the re-fingerprint the add-on already performs at write time. What the fingerprint cannot cover is TRUNCATION — an absence read out of a capped list is not an absence, and "not in the read" and "not on the target" produce the same fingerprint — so a subject missing from a truncated read is blocked at the add-on, where the cap is known, rather than planned as a create that would make a second account for somebody who already has one
- [x] 17.6 `addons.Plan` and `addons.Subjects` — the read legs the backend had no client for. Nothing called the add-on's `/plan` or `/subjects`, which is why the entitlement rehearsal, the add-on drift sweep and the unmanaged inventory each had no source of truth to build on. Both go through `doAuthenticated` like every other leg. `Subjects` deliberately tolerates a stale answer and labels it, and `SubjectsResult.Usable()` states the rule once — a read that is not current, or that hit the add-on's cap, cannot support the sentence every consumer of it writes, which is that an account is NOT there
