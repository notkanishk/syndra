- [x] 1.10 Thread `target` through the propagation claim, drain, and terminal-state writes in `services/propagation`; the drain claims one target per pass and skips targets whose registry state is not `active`. Both conditions live in the claim, not in the drain: the function is exported, and an invariant a caller enforces is one the next caller can skip. This was not cosmetic — the moment a second target registers, the existing drain would claim its rows and push them through the Management API path, where a TrueNAS row has no project and no roles to send. The row carries its `target` so the drain can see what it is holding, and `FOR UPDATE OF p` locks the outbox rows only: locking the `targets` row it joined for the state check would serialise every drain against every registry write. A pass reports the active targets it did **not** dispatch, because a drain that emptied one queue while another waits is otherwise indistinguishable from a drain with nothing left to do — and a failure to list them is non-fatal, since the work it did dispatch still happened. Every claim path is scoped, including the ones that name specific rows: `DrainOne` and `DrainBatch` both hand whatever they claim to the Zitadel dispatcher, which would mark an add-on entitlement (`op_type='apply'`) terminally failed as an unknown operation, with no way back from `failed`. Scoping the claim rather than claiming and releasing is the point — releasing costs on every route, and a requeue spends a retry and records a dispatch failure for a dispatch that never happened, so a handful of targeted applies would exhaust an add-on row's budget before its dispatcher exists and its first genuine transient response would halt it. Not claiming costs nothing. A declined claim is explained by a read rather than by a claim: the target is named in `Awaiting`, once per target rather than once per row, and only for rows that are genuinely unresolved on another active target. Add-on targets get their own dispatcher and their own pass in group 4. every terminal-state write is now guarded by `status='in_flight'` and reports a row it did not match as `ErrPropagationNotInFlight`, because deregistration can terminate a claimed row while its dispatch is out — and an unguarded requeue would return that row to `pending` on a target that no longer exists, recreating the undrainable row the deregistration had just resolved, beyond the sweep that already ran. The drain counts these as `Abandoned`: not a failure, since the call may have reached the target, and certainly not a success, since nothing confirmed it

- [x] 1.20 Per-`(subject, target)` serialization and stale-version rejection in the drain. Serialization is already stronger than the requirement and no new mechanism was built for it: the session-level drain advisory lock admits one drain at a time, the background revocation runner shares it rather than taking its own, and within a pass rows are processed sequentially in `intent_seq` order — so two applies for one subject cannot interleave anywhere. Rejection is the new content. `terminateSuperseded` settles an overtaken row **before** the claim, so a stale version is rejected without ever reaching a dispatcher, and it lives inside all three claim paths rather than beside them — the same reason the active-target join is a condition of the claim. The predicate reads the version off the row's own approval chain (outbox → plan subject → snapshot) rather than taking it as an argument, because a version supplied beside a row can describe a decision that never existed; it fires only when a **settled** (`applied`) row for the same `(subject, target)` carries a strictly greater version, since an unsettled later row is not proof the target moved — the drain still dispatches both, in order. Zitadel rows fall out naturally: their plan subject carries no snapshot, so the join drops them, and their ordering is held instead by the claim never inverting a subject's own intent order (1.26)

- [x] 1.24 Background revocation drain: `propagation.DrainRevocations`, wired as a `periodic.Runner` beside expiry and drift (`REVOCATION_DRAIN_ENABLED`, default on — a revocation nobody drains is retained access, so the safe default is to drain it). Only unreached is retryable and indeterminate is neither a success nor a failure — retrying it duplicates a mutation and counting it either way asserts what the backend does not know. The registration is read under `FOR UPDATE` by the **write itself**, in a locking CTE, not merely by the gate ahead of it — the enqueue is exported, so a lock one caller takes is not an invariant. An unlocked join is an MVCC read: a caller can begin while the target is active, have a deregistration disable it and sweep its queued work, and still commit a fresh row behind that sweep. Under `FOR UPDATE`, READ COMMITTED re-checks the predicate against the version it locked, so a concurrent disable turns into no match; and if the lock is taken first, the disable waits and then abandons what was written. ## Sequencing

226 tasks across 12 working groups. Two dependencies decide the order everything else falls into.

**1.5 (plan storage) gates the back half of §2 and all of §3.** Merging the plan and the snapshot onto one per-subject row means plan storage is schema, not handler state — so 2.17 through 2.26 (plan handler, apply gate, secret exclusion, provisional plans) and the entire Zitadel retrofit wait on it. §2's first sixteen tasks — manifest types, registry, client, redaction, enqueue, `addon_operations` — do not.

**A first commit that stands alone is 1.1–1.7 plus their guards.** Schema only, no behaviour change, revertible: the registry, the outbox rename and reshape, snapshots, plan storage, the drift target dimension. Everything downstream assumes it, and nothing about it assumes anything downstream.

**Group sizes**, for planning rather than for pride: §1 27, §2 52, §3 9, §4 17, §5 15, §6 24, §7 12, §8 14, §9 26, §10 11, §11 10, §12 7.

**§11 goes last on purpose.** It deletes the LLDAP path, and the vault reduction inside it is the point of no return — once the hashes are dropped, every member re-enrols and returning to LLDAP means doing it again.
